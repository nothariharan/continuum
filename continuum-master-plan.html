Part 0 — The One-Sentence Thesis

Every enterprise search and RAG tool answers "what documents mention this?" Continuum answers "what is actually true right now, what used to be true, who or what changed it, and can you prove it?" — and it can only do that because it is built on a graph that keeps every past state instead of overwriting it.

Glean, Tamr, Senzing, Reltio, and every other enterprise-knowledge vendor resolve conflicting facts by picking a winner and quietly discarding the loser. Continuum's entire bet is that the discarded version is the valuable part — that enterprises don't actually trust AI-generated answers today precisely because there's no way to see the reasoning or the history behind them. This is not a search product. It is a system of record for organizational truth.

Part I — The North Star: Continuum at One Year

Before deciding what to cut for nine days, it's worth being explicit about what "no compromises" looks like. Everything in Part II is a deliberate subset of this — not an incomplete version of it, a correct first slice of it.

Months 1–3 — Foundation: prove the core loop on real, messy data

  • Live connectors, not batch exports — webhook-based ingestion for Slack, Gmail, GitHub, Linear, Jira, Google Drive, HubSpot, Confluence, Fireflies, each normalized into the same claim schema within seconds of a source event, not a nightly batch job.
  • Production-grade identity resolution — a trained (not just heuristic) entity-resolution model: blocking via embeddings + string similarity, pairwise classification via a fine-tuned small model (not a raw LLM call per pair — too slow and too expensive at real company scale), active-learning loop where every human correction becomes a training example that improves the next batch's precision.
  • Confidence calibration — every claim, every alias link, every resolved entity carries a calibrated probability, not an arbitrary score. Calibration is checked against a held-out labeled set continuously, and the threshold for "definitive" vs. "contested" vs. "abstain" is tuned to a target precision, not a guess.
  • Source authority as a learned signal — instead of hand-set weights ("HubSpot beats Slack for deal status"), authority per (source, claim-type) pair is learned from historical correction data: which source was right the last 500 times this type of conflict came up?
  • The adjudication workflow becomes a product surface — when the system is uncertain, it doesn't just abstain silently; it queues the contested claim for a human (or a designated "source of truth" agent) to resolve, and that resolution becomes a permanent, versioned edge with an audit trail: who decided, when, based on what evidence.

Months 4–6 — Product: turn the graph into something a company actually operates on

  • The Resolved Fact API — other AI agents (support bots, sales assistants, internal copilots) call Continuum at query time to get a resolved, provenance-backed answer instead of doing their own retrieval — the same pattern Tilores uses for identity, generalized to arbitrary organizational facts. This is the actual GTM wedge: sell the API to teams already building internal agents, not the dashboard to executives.
  • Change alerts — subscribe to an entity ("notify me if ownership of the Acme account changes, or if a contradiction appears that nobody resolves within 48 hours"). This turns Continuum from a thing people query into a thing that pushes signal to people — the actual retention driver for an enterprise product.
  • Org dependency / bus-factor analysis — the "what breaks if this person leaves" traversal, properly built: walks OWNS / RESPONSIBLE_FOR / REVIEWS / MAINTAINS edges outward from a Person node, weights by criticality (production service > internal doc), and produces a real risk score per person, refreshed continuously, not a one-off demo query.
  • Compliance and audit exports — SOC 2 / ISO-style evidence packages: "show me every decision the system made about vendor risk in Q2, and the evidence chain behind each one," exportable as a signed, timestamped report. This is the wedge into legal/compliance buyers who are explicitly blocked on AI trust today.
  • Governance and PII controls — per-source and per-entity-type access control, redaction rules for sensitive fields, row-level security so a resolved fact about a person is only visible to people entitled to see it, not everyone who can query the graph.

Months 7–9 — Scale: multi-tenant, enterprise-grade, defensible

  • Multi-tenant isolation at the HydraDB namespace level — each customer's graph is fully isolated, never cross-queryable, matching HydraDB's own namespace/collection model.
  • SSO / SCIM, role-based access, data residency options — the unglamorous enterprise checklist that actually gates procurement.
  • Self-serve onboarding — connect 2–3 sources, get a working truth graph in under 15 minutes, no professional-services engagement required for the first value moment. Land small (one team's ownership graph), expand to the whole company.
  • Benchmark leadership as a marketing asset — publish our own numbers against Enterprise RAG Bench and HERB the way HydraDB publishes LongMemEval numbers; make "verified against a public benchmark" part of the sales pitch, not just the hackathon submission.

Months 10–12 — Platform: become infrastructure other things are built on

  • Integration marketplace — let third parties write connectors and claim-extraction plugins for niche internal tools (internal wikis, custom CRMs, ticketing systems) against a published schema, the way Segment or Zapier built ecosystems around a converged data model.
  • Vertical templates — pre-built ontologies for specific industries (SaaS sales org, professional services firm, engineering org) so a new customer starts from a tuned schema instead of a blank graph.
  • An "org chart that updates itself" as the flagship free-tier hook — genuinely useful on day one even before deep entity resolution is dialed in, and a natural viral loop inside a company (people want to see and correct their own reporting line).

None of Part I is required reading for the hackathon judges. It exists so that every scoping decision in Part II is a deliberate cut of a real destination, not an improvised feature list — and so the README and demo video can credibly say "here's the wedge we're proving in nine days, here's where it goes" without that being empty hackathon puffery.

Part II — What We Are Actually Building in Nine Days

The slice of Part I that is both fully buildable by a small team in nine days and proves the entire thesis — not a diluted version of the vision, a complete, correct instance of its smallest useful form.

In scope (the MVP — every one of these must work end-to-end and be tested, not just coded)

  1. Three data sources — Slack, GitHub (or Linear, whichever has cleaner sample data available), Gmail. Chosen because together they cover the three claim types that matter most for the demo: discussion (Slack), work/ownership (GitHub/Linear), and external commitment (Gmail).
  2. Three entity types — Person, Project (folds in "Issue"), Account (customer/deal). Enough to tell a complete story, not so many that ontology alignment eats the whole nine days.
  3. Identity resolution — the literal "Sam / @soham / S. Ratnaparkhi" problem, solved with a blocking + pairwise-scoring + clustering pipeline, tested against a hand-labeled ground-truth set we build ourselves.
  4. Claims, not resolved facts — every extracted statement is stored as a versioned, source-attributed Claim; nothing is silently overwritten.
  5. Contradiction detection — when two claims conflict on the same (subject, predicate), the system flags it, applies a source-authority + recency score, and returns a contested answer with both sides shown, not a silent pick.
  6. Bitemporal ownership tracking — the flagship feature: "who owns X now," "who owned it before," "when did it change," "why do we believe that," using HydraDB's native versioned edges (valid_from / valid_to), not a hand-rolled snapshot table.
  7. Provenance ("Why?") — every answer returns its full evidence chain, walkable in the UI.
  8. Three-way abstention — every query returns definitive, contested, or absent — never a confident-sounding guess when the graph has no path.
  9. A held-out evaluation harness — run against Enterprise RAG Bench and/or Salesforce HERB (or our own withheld labeled set if those don't fit our narrow slice cleanly), reporting real precision/recall/abstention numbers, not just a scripted demo.
  10. A working dashboard — search → resolved-state card → expandable "Why?" → ownership timeline. Functional, not beautiful.

Explicitly out of scope for the hackathon (Part I features we are not attempting)

  • Live/webhook connectors — batch ingestion of exported/sample data is fine.
  • A trained entity-resolution model — heuristic blocking + LLM-assisted pairwise scoring is enough; no time to collect training data for a real classifier.
  • The Resolved Fact API for other agents, change alerts, compliance exports, multi-tenant isolation, SSO — all real, all Year-1 material, none of it demoable in a way that matters more than the core loop working.
  • All nine of the brief's source systems — three is enough to prove identity resolution and contradiction handling generalize; adding six more sources without more entity types or harder claims doesn't strengthen the thesis, it just adds ingestion labor.

Stretch, in strict priority order (attempt only after the MVP passes its own held-out eval)

  1. Org dependency / "what breaks if X leaves" traversal — a real Year-1 feature, cheap to demo, expensive to test properly; only attempt if Day 6's eval numbers are already solid.
  2. A fourth data source (Jira or Google Drive), same entity types.
  3. A lightweight "trust score" panel per entity (# corroborated vs. disputed claims) on the dashboard.

Part III — Data Model

The core modeling decision: we never write a resolved fact directly. Everything starts life as a Claim; resolution is a derived, explainable, versioned view over the claims — this is the entire mechanism the whole pitch depends on.

Nodes

NodeKey propertiesNotes
Personid, canonical_name, primary_emailCanonical, post-resolution identity node
PersonMentionid, raw_name, source, source_idRaw, pre-resolution mention ("@soham", "S. Ratnaparkhi", "Sam")
Projectid, name, source_systemFolds in "Issue" for MVP scope
Accountid, nameCustomer / deal entity
Claimid, subject_id, predicate, object, source, source_ref, observed_at, extracted_confidenceThe atomic unit of truth — never mutated, only superseded
Adjudicationid, claim_ids[], decided_by, decided_at, rationaleA human or trusted-agent resolution of a contested claim set
Sourceid, system, authority_weightSlack / GitHub / Gmail, each with a configurable base authority score

Edges

EdgeMeaning
PersonMention -ALIAS_OF-> PersonResolved identity link, carries a confidence score
Claim -ABOUT-> Person|Project|AccountWhat entity the claim describes
Claim -SOURCED_FROM-> SourceProvenance root
Claim -CONTRADICTS-> ClaimAuto-detected conflicting pair, same (subject, predicate), different object
Adjudication -RESOLVES-> ClaimLinks a human decision back to the claims it settled
Person -OWNS {valid_from, valid_to}-> Project|AccountThe flagship bitemporal edge — never overwritten, only superseded by a new edge with a new valid_from
Project -DEPENDS_ON-> Project|AccountPowers the stretch "what breaks if X leaves" traversal

Reference query — the flagship "current + history + why" question

// Current owner
MATCH (p:Person)-[o:OWNS]->(x {id: $entityId})
WHERE o.valid_to IS NULL
RETURN p.canonical_name AS current_owner, o.valid_from AS since

// Full ownership history, most recent first
MATCH (p:Person)-[o:OWNS]->(x {id: $entityId})
RETURN p.canonical_name AS owner, o.valid_from, o.valid_to
ORDER BY o.valid_from DESC

// Provenance: why do we believe the current owner is correct
MATCH (x {id: $entityId})<-[:ABOUT]-(c:Claim)-[:SOURCED_FROM]->(s:Source)
WHERE c.predicate = 'owns' AND c.observed_at >= $currentOwnerSince
RETURN c.source, c.observed_at, c.extracted_confidence, s.system
ORDER BY c.observed_at ASC

// Contradiction check for a given claim set
MATCH (c1:Claim)-[:CONTRADICTS]->(c2:Claim)
WHERE c1.subject_id = $entityId
RETURN c1, c2

Exact Cypher shape should be validated against HydraDB's real OpenCypher subset on Day 1, same discipline as any traversal-heavy submission — treat this as the intended shape, not a guaranteed-correct call.

Part IV — Day-by-Day Execution Plan (Aug 12–20)

Two-role split shown throughout (Product/Data and Engineering) — collapse or expand roles freely for your actual team size. Every day has a hard exit criterion; if a day's exit criterion isn't met, the next day starts by fixing that before adding anything new.

Day 1 — Wed Aug 12 — Foundations

Goal: HydraDB running, schema locked, dataset understood, test questions written.

Product/Data: Download and inspect Enterprise RAG Bench and Salesforce HERB — understand their format, decide whether to eval against them directly or build our own small held-out labeled set that mirrors their structure. Lock the 3-source / 3-entity-type scope (Part II) as final, not a placeholder. Write 15 concrete test questions spanning simple lookup, multi-hop, contradiction, and abstention. Draft README skeleton and demo video outline (problem → project → demo → HydraDB usage, matching the required structure exactly).

Engineering: Stand up HydraDB locally via Docker, verify a round-tripped write + read (not just a listening port). Write schema.cypher with CREATE CONSTRAINT statements for every node type in Part III. Set up repo skeleton: ingestion/, graph/, api/, ui/, eval/, tests/. Basic CI (pytest on push).

Exit criteria: HydraDB node answers a hand-written CREATE + MATCH query; schema committed; dataset downloaded and understood; 15 test questions written and reviewed by both roles.

Day 2 — Thu Aug 13 — Ingestion v1 (One Source, End to End)

Goal: A real slice of Source 1 fully ingested as Claims — prove the pipeline shape before scaling to three sources.

Product/Data: Hand-label 50 documents from Source 1 for ground truth: entity mentions, aliases present, any contradictions visible. Draft the source-authority rubric (which source wins by default for which claim type, before any learned scoring — e.g. "GitHub wins for code-ownership claims, Gmail wins for external-commitment claims").

Engineering: Build entity-mention extraction (LLM-based NER over raw documents → candidate Person/Project/Account mentions + Claim triples). Write the batched Cypher writer (UNWIND, not one write per node). Implement basic alias-candidate generation: name similarity, email match, username match.

Exit criteria: Source 1 (e.g. Slack) is fully ingested into HydraDB as Claim + PersonMention nodes; manual spot-check of 20 records confirms correctness against the hand-labeled set.

Day 3 — Fri Aug 14 — Identity Resolution Engine

Goal: Build and validate the actual "hard part" the brief names by name.

Product/Data: Expand the hand-labeled set to explicitly cover alias-resolution cases across sources (the "Sam / @soham / S. Ratnaparkhi" pattern, using our own analogous examples from the sample data). Define the confidence threshold for auto-merge vs. "needs adjudication."

Engineering: Implement the full pipeline: blocking (candidate pairs via name/email/username similarity) → pairwise scoring (feature-based + LLM-assisted for ambiguous cases) → clustering (union-find) → canonical Person node creation with ALIAS_OF edges carrying confidence scores. Wire this into ingestion for Source 2.

Exit criteria: Identity resolution runs against the labeled alias test set with measured precision/recall reported in a scratch file (not yet the README — that comes Day 9). Source 2 ingested.

Day 4 — Sat Aug 15 — Contradiction Detection + Third Source

Goal: All three sources ingested; contradiction detection live; source-authority scoring wired in.

Product/Data: Finalize source-authority weights based on Day 2's rubric. Write 10 more test questions specifically targeting planted contradictions.

Engineering: Ingest Source 3 (Gmail). Implement contradiction detection: same (subject, predicate), different object, overlapping or ambiguous valid-time windows → flag as CONTRADICTS edge. Implement the three-way response classifier at the query-function level (definitive / contested / absent) — doesn't need an API yet, just correct logic.

Exit criteria: all three sources ingested; the planted/known contradictions in the test set are correctly detected and flagged; three-way response classification verified against the Day 4 test questions.

Day 5 — Sun Aug 16 — Bitemporal Ownership Engine (the flagship feature)

Goal: Implement "who owns X now / before / when did it change / why" — the single feature that most directly proves the whole thesis.

Product/Data: Write the exact flagship demo scenario (an Account or Project with a real, verifiable ownership change in the sample data) and manually verify the correct answer by reading the source documents directly.

Engineering: Implement OWNS / RESPONSIBLE_FOR edges using HydraDB's native versioned-edge (valid_from/valid_to) model — a new edge on ownership change, old edge's valid_to set, never deleted. Implement: current-state query, as-of-time-T query, full-history query, and the provenance-path return (source → claim → adjudication if any → resolved edge).

Exit criteria: given a Person + topic, the system correctly returns current owner, all previous owners with exact change dates, and the full evidence chain — verified against both the Day 1 and Day 5 test questions.

Day 6 — Mon Aug 17 — Multi-Hop, Abstention & the Held-Out Eval Harness

Goal: Multi-hop queries work; abstention is correct; build the thing most competing teams will skip — a real blind test.

Product/Data: Assemble the held-out question set (a portion of Enterprise RAG Bench / HERB, or a withheld slice of our own labeled set never used to tune the pipeline). Define exactly what "correct" means per question category, in writing, before running anything.

Engineering: Implement bounded multi-hop traversal (2–3 hop, e.g. "who on the team responsible for Account X has an open blocking claim against them"). Implement abstention: no path within N hops and confidence below threshold → return absent, never a guess. Build eval/run_eval.py — one command, ingests the frozen graph, runs the held-out question set, prints precision/recall per category (lookup, multi-hop, contradiction, abstention) plus p50/p95 latency.

Exit criteria: run_eval.py runs end to end and produces a results file with real numbers — this is the artifact that goes in the README on Day 9, not a placeholder.

Day 7 — Tue Aug 18 — API + Dashboard v1

Goal: Everything usable through a UI a judge can operate without touching raw Cypher.

Product/Data: Write the exact shot list for the demo video against the flagship scenario. UX pass on the dashboard — search bar, resolved-state card, expandable "Why?", ownership timeline.

Engineering: FastAPI endpoints: /ask, /entity/{id}/history, /entity/{id}/why, /contradictions — thin layer over the Cypher queries, no traversal logic in the API itself. Build the dashboard (React or plain HTML+JS if time is short): search → resolved card → provenance chain → timeline.

Exit criteria: the flagship demo scenario is fully answerable end to end through the UI, with no developer intervention or raw query typing.

Day 8 — Wed Aug 19 — Stretch Feature (conditional) + Hardening

Goal: Attempt exactly one stretch feature — and only if Day 6's eval numbers were genuinely solid. Otherwise, this entire day is hardening.

Product/Data: If eval numbers were weak: help re-diagnose failure categories, expand the labeled set, re-test. If strong: write draft README sections (problem statement, architecture diagram description, HydraDB usage explanation, eval results table).

Engineering: If eval passed cleanly: build the org-dependency/"what breaks if X leaves" traversal (highest-priority stretch, per Part II). If not: spend the day exclusively fixing precision/recall regressions from Day 6 — no new features.

Exit criteria: either the stretch feature is fully working end to end, or it was explicitly cut — no half-built feature ships in the final repo. Re-run run_eval.py and confirm numbers didn't regress.

Part VI — Demo Script (3 minutes, shot by shot)

  1. 0:00–0:25 — The problem. "Your company's Slack, GitHub, and email all know something different about who owns this account. Search tools show you all three and make you guess. We built a graph that tells you which one is right, when it became right, and why."
  2. 0:25–0:55 — What we built. Quick architecture beat: three sources → claims, not overwritten facts → identity resolution → bitemporal ownership graph in HydraDB.
  3. 0:55–2:20 — Live demo. Ask "who owns [flagship entity] right now?" → resolved-state card appears. Click "Why?" → provenance chain expands, showing the actual source claims. Ask "who owned it before?" → timeline animates, shows the change and the date. Ask a deliberately contested question → system shows both claims side by side instead of guessing. Ask a question with no answer in the data → system says so, explicitly.
  4. 2:20–2:50 — HydraDB usage. "Every one of those answers is a native traversal over HydraDB's versioned edges — the ownership history isn't a table we maintain, it's the graph's own append-only history. Without HydraDB we could show you documents. With it, we show you what changed, when, and why we believe it."
  5. 2:50–3:00 — Close. One-line eval stat on screen (e.g. "X% precision on held-out questions, verified against Enterprise RAG Bench").

Part VII — Risk Register

Risk: Identity resolution precision is too low to trust in a live demo. Mitigation: Day 3 has a hard exit criterion tied to measured precision/recall on the labeled set — if it's weak, Day 8 becomes a hardening day instead of adding stretch features, by design.
Risk: Team spends too long hand-rolling ingestion instead of using existing tooling. Mitigation: Scope is fixed to 3 sources / 3 entity types from Day 1 — no mid-hackathon scope expansion without cutting something else first.
Risk: Demo looks good but the held-out eval was never actually run. Mitigation: Day 6's exit criterion is a literal command (run_eval.py) that must produce a results file — this is treated as non-negotiable as the dashboard itself.
Risk: Cypher/HydraDB traversal ends up being done in Python against data pulled out of the graph (the "JSON store with a HydraDB label" failure mode). Mitigation: Every query in Part III is written as Cypher first; the API layer's job is explicitly to contain zero graph-walking logic of its own, called out at every engineering task above.
