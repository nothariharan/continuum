Continuum

One-Year Architecture, Engineering Plan, HydraDB Integration Strategy & Demo Direction

This plan treats the Hack Hydra Track 01 submission as the first vertical slice of a one-year product. The core goal is to build the state/context layer between messy enterprise systems and the humans or AI agents that need reliable organizational context.

Core thesis: Continuum is not a chatbot sitting on top of enterprise documents. It continuously turns fragmented enterprise evidence into a resolved, temporal, explainable graph of the organization, then exposes that state through search, APIs, MCP and other integrations.

1. What We Are Building

The official Track 01 challenge asks for a clean, queryable ontology over roughly half a million enterprise artifacts, with entity resolution and ontology alignment as central difficulties. citeturn0file5 Continuum should solve that foundation, then extend it into a general organizational state engine.

2. Why HydraDB Should Shape the Architecture

The current open-source HydraDB repository describes an object-store-native distributed graph database written in Rust, with durable graph storage on SlateDB, snapshot-consistent OpenCypher, GraphBLAS traversal, Neo4j-compatible Bolt, HTTP/NDJSON APIs, separate graph-node and graph-indexer roles, property indexes, reverse adjacency and bounded runtime behavior. citeturn0file0turn0file1

HydraDB primitiveContinuum usage
OpenCypher + graph plannerAll important relationship/state queries execute inside HydraDB; do not pull the graph into Python for core reasoning.
GraphBLAS traversalNative bounded multi-hop traversal for ownership, dependency and impact questions.
Property indexes + reverse adjacencyFast entity seeding and “who/what points to X?” queries.
Snapshot consistencyEvery answer and its evidence are evaluated against a coherent graph snapshot.
WAL + immutable traversal indexesSupport continuous ingestion without rebuilding the whole graph synchronously.
Object-store durabilityKeep long-tail organizational state cheaply and use local SSD/NVMe for hot working data.
SPpaths / SSpaths / MSpathsUse native bounded path operations, especially MSpaths to avoid client-side query fan-out. citeturn0file2
Bounded executionGive every user query explicit hop/result/time/token budgets. citeturn0file0

The HydraDB README explicitly describes traversal over compiled CSC topology plus visible WAL state under a pinned snapshot, and its MSpaths procedure is designed to evaluate many sources/targets together rather than fan out from the client. citeturn0file2

4. Use a Layered Graph, Not a Flat Document Graph

Layer 1 — Evidence

Source artifacts and events: messages, threads, PRs, issues, documents, meetings, assignments, status changes and other source objects.

Layer 2 — Claims

Atomic, source-attributed statements extracted from evidence. Claims are never silently overwritten.

Layer 3 — Canonical Entity Graph

People, teams, projects, accounts, services, repositories, decisions, issues and other canonical entities linked by typed relationships.

Layer 4 — Resolved State

Derived current or historical state after time, corroboration, conflict rules, permissions and confidence are applied.

RAW EVIDENCE
     |
     v
   CLAIMS
     |
     v
ENTITY GRAPH
     |
     v
RESOLVED STATE

Normal questions should operate over Layers 3–4. Evidence should be loaded lazily when the user asks “why?” or the state resolver needs supporting claims.

6. Temporal State: The Differentiator

Use a bitemporal mental model whenever the source data supports it:

T_valid = when the fact was true in the business world
T_tx    = when Continuum learned / recorded the fact

Example: a Gmail received Aug 10 says Sarah will own Acme starting Aug 15. Then T_tx=Aug 10, T_valid_from=Aug 15. This enables “who owns Acme now?”, “who owned it on Aug 1?” and “what did Continuum know on Aug 12?”

Recent temporal GraphRAG research supports explicitly modeling time and narrowing retrieval to temporal scope. TG-RAG models timestamped relations and incremental temporal updates; T-GRAG focuses on temporal conflicts/redundancy; STAR-RAG uses time-aware propagation to reduce the context candidate set. citeturn970561academia29turn970561academia28turn970561academia30

8. Query Planner: Specialize the Hot Paths

Do not make arbitrary LLM-to-Cypher the default. Build typed semantic operations:

resolve_entity(entity_text)
get_current_state(entity, predicate)
get_state_as_of(entity, predicate, time)
get_history(entity, predicate, range)
get_conflicts(entity, predicate)
get_evidence(state_id)
get_dependencies(entity, depth)
get_impact(entity, depth)

Compile each operation to known, tested Cypher/native-path plans. HydraDB supports bounded variable-length paths, filters, aggregation, pagination and native SPpaths/SSpaths/MSpaths. citeturn0file2

9. Query Budgets

Every request receives a predictable computational budget:

max_hops
max_nodes
max_edges
max_evidence
max_latency
max_tokens

Examples:

QuestionExecution
Who owns Acme?Entity lookup → reverse OWNS traversal → state resolver.
Who owned Acme last month?Entity lookup → temporal filter → bounded ownership traversal.
Why is Acme blocked?State → blocker relationship → strongest claims → evidence snippets.
What depends on this service?Reverse bounded traversal / native path procedure.
What breaks if Sarah leaves?Bounded multi-hop impact traversal with criticality filters.

10. Keep LLMs on the Ambiguous / Explanatory Tail

The default should be:

Do not spend LLM calls on structured source metadata or deterministic state queries. Use models for claim extraction, ambiguous identity matching, ontology suggestions, query interpretation and final explanations.

12. Cache State, Not Just Raw Queries

Prefer semantic cache keys such as:

(entity_id, predicate, temporal_scope, permission_scope, graph_snapshot)

Invalidate locally when affected state changes. Example: a change to Acme ownership should invalidate Acme.current_owner and related impact/history views, not the entire graph cache.

13. Evidence Should Be Lazy

Most answers should return a small resolved state immediately. Only “Why?” or contested answers should fan out to original evidence.

14. HydraDB Engineering Rules

  1. Never perform the core graph walk in Python.
  2. Use property indexes for entity seed lookup.
  3. Exploit reverse adjacency for reverse-ownership/dependency queries.
  4. Use bounded paths.
  5. Use SPpaths/SSpaths/MSpaths when they materially reduce query fan-out.
  6. Use batched UNWIND writes rather than one write per node/edge.
  7. Keep provenance traversal inside HydraDB where practical.
  8. Use causal reads for normal hot-path queries; use strong reads only when immediate visibility after a write matters. citeturn0file2
  9. Profile before modifying HydraDB internals.
  10. Do not turn HydraDB into a generic document store just to say it is being used.

22. Final Engineering Priorities

  1. Run the real HydraDB smoke test: write, read, delete, reopen and traverse. The repository explicitly notes that an open port is not proof that the database works. citeturn0file2
  2. Freeze the claim/state model.
  3. Implement entity resolution as a measurable subsystem.
  4. Implement typed query plans.
  5. Benchmark HydraDB traversal/query shapes.
  6. Build the latency/correctness harness.
  7. Add temporal and conflict resolution.
  8. Add provenance.
  9. Add the UI.
  10. Add stretch features only after the core benchmark is stable.

23. Final Product Thesis

Continuum should become the fastest and most trustworthy middle layer between enterprise systems and AI. Retrieval finds evidence. HydraDB reconstructs relationships. Continuum resolves state. Provenance proves it. Agents consume it.

Long-term destination: not “another enterprise RAG product,” but a company-state infrastructure layer that AI agents, internal applications and humans can query to understand what is true, what changed, what is uncertain, why the system believes it, and what is likely to be affected by a change.
