Continuum — The Company Truth Graph

One-Year Master Architecture & Product Plan

This document describes how Continuum should be designed if we were given a full year, a strong engineering team, realistic enterprise access, and the goal of turning the Hack Hydra Track 01 prototype into a serious, integratable product. The nine-day hackathon version is deliberately treated as the first vertical slice of this larger system, not as a separate architecture.

Core thesis: Continuum should not become “another enterprise search engine.” Its job is to reconstruct the current state of an organization from fragmented, contradictory, time-dependent evidence and expose that state as a trustworthy, queryable layer for people, applications, and AI agents.

1. Executive Product Definition

Continuum is a persistent enterprise state layer that sits above the systems a company already uses. Slack, Gmail, GitHub, Linear, Jira, Confluence, Drive, CRM systems, meeting systems, ticketing platforms and future internal applications continue to be the systems where work happens. Continuum does not attempt to replace them.

Instead, Continuum continuously converts their events and artifacts into a resolved organizational model:

Enterprise systems
  ↓
Artifacts / events
  ↓
Claims
  ↓
Identity resolution + entity linking
  ↓
Ontology / relationship graph
  ↓
Temporal state + contradiction engine
  ↓
Resolved enterprise state
  ↓
Provenance + confidence + permissions
  ↓
APIs / MCP / agents / search / dashboards / automation

The product should answer questions that ordinary search systems struggle with:

  • Who owns this account right now?
  • Who owned it last month?
  • When and why did ownership change?
  • Which systems disagree?
  • What evidence supports the current state?
  • What is the latest trustworthy state of this project?
  • Who is the real technical owner of this service?
  • What decisions led to the current architecture?
  • What breaks if this person leaves?
  • Which customers, projects, systems or teams depend on this person?
  • What information is missing?
  • What was believed at a previous point in time?

The important product shift is from document retrieval to organizational state reconstruction.

2. The Competitive Positioning We Should Build Around

Based on the research already assembled for this project, the market contains several major categories. The objective is not to claim that competitors have no graph capabilities or no temporal capabilities. The objective is to identify a specific capability that Continuum can own and make central.

CategoryRepresentative systemsCore jobWhere Continuum should differ
Enterprise search / copilots Glean, Microsoft 365 Copilot, Google/Gemini enterprise search, Slack AI, Notion AI, Guru, Rovo Find and synthesize information across enterprise applications. Continuum should return a resolved state with evidence, history, conflicts and relationships rather than primarily returning document snippets.
Enterprise knowledge / data platforms Palantir, Databricks, Snowflake and similar platforms Unify enterprise data and enable analytics/AI workloads. Continuum should focus on the semantic “what is true?” layer: identity, claims, ownership, state transitions, provenance and agent-facing context.
Graph databases / GraphRAG Neo4j, Memgraph, Kuzu, FalkorDB, Microsoft GraphRAG and related ecosystems Represent relationships and improve retrieval/reasoning. Continuum should package graph capabilities into a complete enterprise-state product, including claims, temporal resolution, contradiction handling, provenance and integrations.
Agent memory Mem0, Zep/Graphiti, Letta and related memory systems Persist agent/user information across sessions. Continuum should model organizations rather than just user/session memory and should make state first-class, with enterprise permissions and provenance.
Master data / identity resolution Reltio, Tamr, Senzing and similar systems Resolve entities and maintain trusted records. Continuum can apply the same identity principle to dynamic organizational facts and relationships, rather than only canonical customer/person records.

Our competitive wedge should therefore be narrow and defensible:

Continuum is a resolved enterprise state engine. It continuously determines which entities and claims refer to the same real-world things, tracks state over time, detects conflicting evidence, computes a current state, preserves the evidence behind that state, and exposes the result to applications and agents.

Do not market the first version as “better Glean.” Do not market it as “GraphRAG with a UI.” Do not market it as “a knowledge graph chatbot.” Those descriptions collapse the product into already crowded categories.

3.2 Source ingestion layer

Each connector should have the same conceptual contract regardless of source:

SOURCE CONNECTOR
  - authentication
  - permission snapshot
  - historical backfill
  - incremental sync
  - change/webhook handling
  - deletion handling
  - source identity mapping
  - source metadata
  - source timestamps
  - source-specific parser
  - normalized artifact event

A connector should not directly write “facts” into the graph. It should emit normalized artifacts and events.

Examples:

  • Slack message
  • GitHub pull request
  • GitHub review
  • Linear issue update
  • Gmail thread
  • Google Drive document version
  • HubSpot deal update
  • Fireflies transcript
  • Jira assignment

This lets the source layer remain independent from the reasoning layer.

4.5 Resolved State

ResolvedState

- valid_to
- confidence
- status
- supporting_claims
- conflicting_claims
- adjudication

Status should support at least:

  • definitive
  • contested
  • unknown / absent
  • restricted when permissions prevent the answer

5. Temporal Architecture

The temporal model is one of the strongest potential differentiators, but it should remain a mechanism for trustworthy state rather than become a marketing buzzword.

Continuum should track at least two clocks:

T_valid = when the fact was true in the real world

T_tx = when Continuum learned / recorded the fact

Example:

Email received:
July 20

Email states:
"Sarah will take over Acme on August 1."

Therefore:

T_tx = July 20
T_valid_from = August 1

This makes queries such as these possible:

  • Who owns Acme now?
  • Who owned Acme on June 1?
  • What did Continuum believe on July 25?
  • When did the graph first learn that Sarah would take over?
  • Which source caused the state transition?

A future production system should expose this as a standard state-query API rather than requiring every client to understand temporal graph mechanics.

8. Contradiction and Evidence Resolution

Continuum should not pretend every enterprise fact has one globally authoritative source.

Instead, it should calculate evidence strength using a combination of:

  • source system
  • claim type
  • explicitness
  • recency
  • temporal validity
  • number of independent corroborating sources
  • relationship consistency
  • historical source reliability
  • human adjudication

Conceptually:

evidence_score =
  source_reliability
  × claim_type_reliability
  × explicitness
  × temporal_relevance
  × corroboration
  × extraction_confidence

The important product behavior is:

Strong evidence:
    resolved state

Conflicting evidence with a likely winner:
    resolved state + conflict visible

Conflicting evidence with no reliable winner:
    CONTESTED

Insufficient evidence:
    UNKNOWN / ABSTAIN

Permission-blocked:
    RESTRICTED

This is substantially safer than letting a language model “average” contradictory documents.

10. Authorization Architecture

Permissions are not an optional enterprise feature. They are foundational.

Continuum must never become a system that turns information a user could not normally discover into a cross-system leak.

Long-term authorization should include:

  • source ACL ingestion
  • user identity mapping
  • group/team mapping
  • document-level permissions
  • entity-level restrictions where required
  • field-level redaction for sensitive properties
  • graph traversal filtering
  • audit logs

Every query should effectively be evaluated as:

Can this requester see the artifact?
        ↓
Can this requester see the claim?
        ↓
Can this requester traverse this relationship?
        ↓
Can this requester see the resolved state?
        ↓
Return only authorized evidence.

The authorization layer should be designed early, even if the hackathon prototype uses a simplified model.

20. Evaluation Architecture

Evaluation must be treated as a product subsystem, not something added on submission day.

Continuum should maintain multiple test suites.

Entity resolution

  • precision
  • recall
  • merge accuracy
  • false merge rate
  • false split rate

State reconstruction

  • current-state accuracy
  • historical-state accuracy
  • temporal boundary accuracy

Contradiction handling

  • conflict detection precision
  • correct winner selection
  • correct abstention rate

Graph reasoning

  • multi-hop accuracy
  • path correctness
  • explanation completeness

System

  • p50 latency
  • p95 latency
  • ingestion throughput
  • incremental update latency
  • cost per million artifacts

Every release should run regression evaluation automatically.

22. LLM Architecture

LLMs should not be the source of truth.

They should perform tasks where probabilistic language understanding is valuable:

  • claim extraction
  • ambiguous entity matching
  • ontology suggestions
  • natural-language query translation
  • answer explanation
  • summarization

They should not directly determine:

  • final ownership
  • temporal state
  • permissions
  • graph traversal results
  • which conflicting claim wins without evidence scoring

The architecture should follow:

LLM proposes
    ↓
deterministic / graph system verifies
    ↓
resolved state returned
    ↓
LLM explains

34. Final One-Year Prioritization Rule

When deciding whether to build a feature, use this order:

  1. Does it make entity resolution more accurate?
  2. Does it make state reconstruction more accurate?
  3. Does it make history or change more understandable?
  4. Does it make provenance stronger?
  5. Does it make permissions safer?
  6. Does it make Continuum more useful as infrastructure for other software?
  7. Does it strengthen the core data moat?

If the answer is no to all of these, the feature should wait until the core system is strong.

Continuum wins by becoming the most trustworthy layer between messy enterprise information and the AI systems trying to act on it.
